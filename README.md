# Кандидатогенерация для Авито Услуг

Для каждого запроса отбираем 50 объявлений из 189 212. Метрика Recall@50.

## Запуск

Нужны Python 3.13 и видеокарта NVIDIA с CUDA (проверялось на RTX 4060 8 ГБ).

```bash
pip install -r requirements.txt   # torch нужен с CUDA
# положить train.parquet, benchmark_queries.parquet, benchmark_items.parquet в data/
python run.py
```

На выходе `answer.csv`, метрики валидации в `reports/validation.json`. `answer.csv` в репозитории
это файл, который отправлен на платформу (0.866).

Путь к данным можно поменять через `AVITO_DATA_DIR`. Модель BAAI/bge-m3 берётся из кэша Hugging Face
(если её нет, веса скачаются один раз, дальше всё работает офлайн). Первый запуск занимает около
20 минут, в основном это эмбеддинги; они кэшируются в `cache/`, повторный запуск около 2 минут.

Сиды фиксированы, LightGBM и torch работают в детерминированном режиме: запуск с нуля и повторные
запуски дают побайтно тот же `answer.csv`. На другой модели видеокарты fp16-вычисления могут
отличаться в последних знаках, тогда возможны небольшие расхождения в порядке близких кандидатов.

## Решение

Две стадии.

**1. Линейный скор по всему каталогу.** Для каждого запроса считаем скор всех объявлений сразу на GPU
(матричное умножение занимает доли секунды), без предварительной отсечки. Скор это взвешенная сумма признаков:

- `dq`, `dqp`: косинус BGE-M3 между запросом (и запросом с фильтрами) и объявлением
  (заголовок + начало описания + начало параметров);
- `lex`: TF-IDF по словам и биграммам, заголовок и параметры с повышенным весом;
- `same`, `trans`, `geo`: та же локация; вероятность перехода из локации поиска в локацию объявления
  по кликам train; расстояние от центра локации поиска до объявления;
- `mc05`, `mcp`: распределение микрокатегорий выбранных объявлений у 20 похожих запросов train
  и по тексту фильтров;
- `dclick`: близость объявления к тем, которые выбирали по похожим запросам train;
- `hist`: сколько раз объявление выбирали по такому же тексту запроса;
- категория, число отзывов.

Веса подобраны перебором на валидации (`src/config.py`).

**2. LightGBM lambdarank** переупорядочивает top-150 первой стадии. Признаки те же плюс рейтинг, цена,
позиция и скор первой стадии, похожесть ближайшего запроса train, размер локации.

Отдельно: если в train есть точно такой же запрос из той же локации, выбранные по нему объявления
ставятся первыми (таких запросов 91).

Почему такие признаки. 84% выбранных объявлений находятся в локации поиска, остальные почти всегда
в соседних, поэтому гео даёт больше всего. Фильтры запроса ("Вид услуги Красота, здоровье") по сути
задают категорию, отсюда `dqp` и `mcp`. По коротким запросам текст объявления часто мало похож на запрос,
а историю выборов по похожим запросам хорошо видно в train, отсюда `mc05` и `dclick`.

Использованы открытые библиотеки и модели: BAAI/bge-m3 (MIT) через sentence-transformers, scikit-learn,
PyTorch, LightGBM.

## Валидация

33 тыс. строк train ссылаются на объявления, которые есть в каталоге бенчмарка. Из них собраны
отложенные запросы: `val` (2000, для оценки) и `trn` (6000, для обучения ранкера), тексты
не пересекаются. Поиск идёт по настоящему каталогу. Для отложенных запросов их строки train не
используются при подсчёте признаков.

В `val` у 83% запросов текст встречается в train, в бенчмарке у 37%, поэтому смотрим на
`R_w = 0.37 * R(текст был в train) + 0.63 * R(новый текст)`.

Проверка на платформе: первое решение даёт 0.779 на валидации и 0.757 на платформе, улучшение первой
стадии +0.103 и +0.084. То есть валидация немного завышает, но варианты сравнивает правильно.

## Что нашли по ходу

- Сначала отбирался top-1000 по тексту по всей стране, и Москва с Петербургом вытесняли остальные города:
  у 431 запроса в кандидатах не было ни одного объявления из своего города. Поэтому скор считается
  по всему каталогу.
- Квота "40 из своего города + 10 со всей страны" тратила 10 мест впустую. Мягкие гео-признаки
  вместо квоты дали самый большой прирост.
- Фильтры запроса не передавались в энкодер. Добавлены `dqp` и `mcp`.
- Признак "сколько раз объявление выбирали в train" дал +0.012 на валидации и +0.001 на платформе:
  все ответы валидации по построению есть в train, и она его переоценивает. Убрали.
- Ранняя валидация на синтетическом каталоге (объявления со всей страны вперемешку) искажала всё,
  что связано с локацией. Заменена на описанную выше.
- Ответ с ранкером отличался от запуска к запуску, хотя LightGBM детерминирован. Причина была в
  `torch.sparse.mm` на GPU: он суммирует в произвольном порядке, признак `dclick` плавал в последних
  знаках, и деревья строились чуть иначе. Перенесли это вычисление на CPU, два запуска подряд дают
  одинаковый `answer.csv`.
- Не помогли: cross-encoder BAAI/bge-reranker-v2-m3 поверх top-100 (+0.002, в пределах шума),
  дообучение convaiinnovations/laya-multilingual как ранкера (переобучалось на шумные негативы).

## Результаты

| Вариант | Валидация R_w | Платформа |
|---|---|---|
| BGE-M3 + TF-IDF, квота по городу | 0.779 | 0.757 |
| линейная стадия: гео, микрокатегории, фильтры | 0.882 | 0.841 |
| то же + популярность объявления | 0.894 | 0.843 |
| линейная стадия + dclick, LightGBM поверх top-150 (без популярности) | 0.909 | **0.866** |
| то же, ранкер на 10000 запросах, 63 листа, 300 деревьев | 0.912 | 0.861 |

Разница между валидацией и платформой держится около 0.04, поэтому варианты выбирались по валидации.
Отличия меньше 0.005 на валидации в пределах шума (последняя строка). Финальный ответ соответствует
настройкам по умолчанию в `src/config.py`.
